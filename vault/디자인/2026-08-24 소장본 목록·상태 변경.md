# 디자인 스펙: 소장본 등록 화면 — 소장본 목록 + 상태 변경

> 범위: `/copies/new` 화면 중 **"소장본 목록" Card**만. "새 소장본 등록" 폼(`CopyRegisterForm`)은
> 이미 구현되어 있어 이 스펙 밖이며, `onCreated` 콜백 prop 추가만 이 작업의 변경 대상이다.
> 입력 형태: 내보낸 React/JSX 코드(`CopyRegistrationScreen`, 브리프 전문 인용) + 백엔드 API 계약(Kotlin) +
> 기존 코드베이스 재사용 컴포넌트 5종. 코드 기반이라 신뢰도가 높으며, 디자인 목업과 실제 백엔드가
> 갈라지는 지점(검색 UX, status 어휘, 컬럼 수)은 브리프의 확정 결정을 그대로 반영했다(임의 해석 없음).

## 개요

"소장본 등록" 화면 하단의 목록 카드. 등록된 소장본(BookItem)을 관리번호/도서명으로 검색해 표로
보여주고, 행별로 상태 변경(분실/폐기) 액션을 제공한다. 서버는 `GET /bookitems`로 검색·페이지네이션된
목록을(`bookTitle` 포함, JOIN 완료 상태), `PATCH /bookitems/{id}/status`로 상태 변경을 제공한다.
디자인 원본(`CopyRegistrationScreen`)은 통합 검색창 1개 + 클라이언트 배열 필터를 쓰는 목업이지만,
실제 구현은 서버 검색(관리번호·도서명 입력 2개, AND 조건) + 서버 페이지네이션 + 재조회 기반 상태
갱신으로 대체한다.

- Button(분실/폐기) × 2는 같은 컴포넌트의 반복 호출일 뿐 신규 variant 불필요

## 상태 & 상호작용

### 검색 (Input × 2)
- 관리번호 입력, 도서명 입력 — 각각 독립 상태. **AND 조건**으로 서버에 함께 전달(`GET /bookitems?managementNumber=...&q=...`)
- 디바운스: `useDebouncedValue`(기본 250ms) 재사용 — 입력마다 요청하지 않음. 두 필드는 각각 별도로 훅을 호출한다(`use-debounced-value.ts` 문서의 "필드마다 한 번씩" 규칙)
- 값이 바뀌면 1페이지로 리셋(서버 페이지네이션 상태와 결합 — `BookListCard`의 `refreshToken`/`prevToken` 렌더 중 조정 패턴 참조)
- 빈 입력 = 필터 없음(두 값 다 비면 전체 목록)

### 표 로딩/에러/빈 상태
- 로딩: `DataTable`의 `loading` prop → 첫 로드는 `loadingText`("불러오는 중…"), 페이지 이동 중엔 기존 행 유지 + `opacity-60`(dimmed) — 재사용 컴포넌트 내장 동작, 별도 구현 불필요
- 에러: 조회 실패 시 표 대신 `ListErrorState`(재사용, 신규 아님) — "다시 시도" 버튼으로 retry 카운터 증가 → refetch (`BookListCard`/`ReturnListCard` "요청 키 vs 완료 키" 패턴 그대로 적용)
- 빈 결과: `DataTable`의 `emptyText` prop — 디자인 원본 문구 "검색 결과가 없습니다." 그대로 사용

### 상태 변경 액션 (행별, 3분기)
서버 `status` 값(`AVAILABLE|ON_LOAN|LOST|DISPOSED`) 기준으로 분기한다. **디자인 목업의
`loaned/overdue/lost/disposed/available` 문자열이 아니라 이 서버 값으로 분기 조건을 작성한다.**

| 서버 status | 상태 변경 셀 표시 | 클릭 동작 |
|---|---|---|
| `AVAILABLE` | Button "분실"(ghost/sm) + Button "폐기"(ghost/sm) | 클릭 → `PATCH /bookitems/{id}/status` (`LOST` 또는 `DISPOSED`) 호출 |
| `ON_LOAN` | `<span>대출 중 변경 불가</span>` (버튼 없음, 비활성 문구) | 없음 — **서버 호출 자체를 막는다**(브리프 확정: UI 정책상 서버는 ON_LOAN도 거부하지 않지만 프론트가 막음) |
| `LOST` \| `DISPOSED` | `<span>—</span>` | 없음(이미 종결 상태) |

- 처리 중(요청 진행 중) 상태: 해당 행 버튼 `disabled` + `aria-busy`(`ReturnListCard`의 `processingIds: Set<number>` 패턴 재사용 권장 — bookItemId 단위로 관리)
- 성공 시: **낙관적으로 배지를 바꾸지 않는다.** Toast(success, 메시지에 도서명 포함 — 예: `"클린 코드" 분실 처리되었습니다.`) 후 목록 재조회(`fetchToken` 증가 방식, `ReturnListCard` 선례)
- 실패 시: Toast(danger). 에러 코드별 분기:
  - `BOOK_ITEM_NOT_FOUND`(404) — 다른 창에서 먼저 삭제/변경된 경합 가능성 → 목록 재조회로 최신 상태 반영 권장(선례: `ReturnListCard`의 `LOAN_NOT_ON_LOAN_CODE` 처리)
  - `INVALID_STATUS`(400) — 도메인 정책 위반(설계상 프론트가 `LOST`/`DISPOSED`만 보내므로 정상 흐름에서는 발생하지 않아야 함) — 토스트로만 노출
- 상태 값 매핑: `toBookItemBadgeStatus()`(`book-table.ts`, 재사용, 신규 아님)로 `BookItemStatus` → `BookStatus`(배지 어휘) 변환 후 `StatusBadge`에 전달. 이 함수를 새로 만들지 않는다.

### 카운트 배지(titleRight)
- 표시값: `pagination.totalElements`(서버 응답, `toLocaleString()`) — 디자인 원본의 `filtered.length`(클라이언트 배열 길이)가 아님. 서버 페이지네이션이므로 총 건수는 서버가 소유.

### hover/focus
- 행 hover: `DataTable` 내장(`hover:bg-surface-muted`) — 재사용, 별도 구현 불필요
- 버튼/입력 hover/focus/disabled: 각 컴포넌트(`Button`/`Input`) 내장 — 재사용, 별도 구현 불필요

## 반응형 규칙

디자인 원본(`CopyRegistrationScreen`)이 고정 픽셀 패딩(`padding:'32px 40px'`)의 데스크톱 전용
레이아웃이고, 이 화면의 다른 재사용 선례(`BookListCard`, `ReturnListCard`)에도 브레이크포인트 분기가
없다 — **이 카드도 반응형 분기 없음(고정 데스크톱 레이아웃)**으로 간주한다. 표 자체는
`DataTable`의 `overflow-x-auto`(내장)로 좁은 뷰포트에서 가로 스크롤만 발생한다.

- base~: 검색 Input 2개 + 표, 컬럼 폭 고정(%) — 별도 스택/그리드 전환 없음
- 미확정: 관리번호/도서명 두 검색 Input을 나란히(가로) 배치할지 스택할지 디자인 원본에 명시 없음(원본은 검색창 1개) → 아래 "미확정 항목" 참조

## 데이터/콘텐츠 형태

```ts
// GET /bookitems 요청 파라미터
type SearchBookItemsParams = {
  q?: string;                  // 도서명·지은이 부분 일치
  managementNumber?: string;   // 관리번호 부분 일치
  page?: number;                // 1-based, 기본 1
  pageSize?: number;             // 기본 10, 최대 100
};

// GET /bookitems 응답 → 행 데이터 shape (DataTable<T> 제약상 `type`, interface 아님)
type BookItemSearchRow = {
  bookItemId: number;
  bookId: number;
  bookTitle: string;            // 서버가 이미 JOIN해서 내려줌 — 클라이언트에서 title 조합 불필요
  managementNumber: string;
  status: "AVAILABLE" | "ON_LOAN" | "LOST" | "DISPOSED"; // = BookItemStatus, 기존 타입 재사용
  createdAt: string;            // 이 화면 컬럼엔 노출 안 함(브리프상 4컬럼: 관리번호/도서명/상태/상태변경)
};

type BookItemSearchResponse = {
  bookItems: BookItemSearchRow[];
  pagination: PaginationMeta;   // 기존 client.ts 타입 재사용 { page, pageSize, totalPages, totalElements }
};

// PATCH /bookitems/{bookItemId}/status 요청/응답
type ChangeBookItemStatusInput = { status: "LOST" | "DISPOSED" }; // 이 두 값만 허용(서버 require)
type ChangeBookItemStatusResponse = {
  bookItemId: number;
  managementNumber: string;
  status: "LOST" | "DISPOSED";
};
```

- 컬럼(4): 관리번호(18%, nowrap) / 도서명(36%) / 상태(14%) / 상태 변경(잔여 %, nowrap 여부 미확정)
- `BookItemStatus`, 매핑 함수 `toBookItemBadgeStatus`, 에러 상수 네이밍 관례(`BOOK_NOT_FOUND_CODE`류)는
  기존 `src/lib/api/bookitems.ts`/`book-table.ts`를 그대로 확장 — 이 스펙에서 새 타입 체계를
  만들지 않는다.

## 미확정 항목 (확인 필요)

1. **검색 Input 2개의 레이아웃**: 가로 나란히 배치인지, `Card padding="sm"` 안에서 flex-row/grid로
   둘지 — 디자인 원본은 통합 검색창 1개뿐이라 참조할 시각 근거가 없음. component-architect/구현
   단계에서 `ReturnListCard`의 검색 Card(`padding="sm"`) 패턴을 준용하되 배치는 확인 필요.
2. **카운트 배지 색**: 디자인 원본은 `CountBadge color="var(--color-copy)" bg="var(--color-copy-light)"`
   (보라색, copy 전용 톤)를 쓰지만, 이 스펙은 `BookListCard` 선례(`Badge variant="soft" tone="neutral"`)를
   기본으로 제안했다. `--color-copy`/`--color-copy-light` 토큰이 이미 `globals.css`에 존재하므로
   `tone="copy"`류를 살릴지, 다른 목록 화면과 통일해 `neutral`로 갈지는 확인 필요(Badge의 tone
   타입에 `"copy"`가 있는지도 `ui/badge.tsx` 확인 필요 — `status-badge.tsx`의 `BookStatus.copy` 매핑은
   `tone: "copy"`를 이미 참조하고 있어 존재 가능성 높음).
3. **분실/폐기 버튼 확인 UX**: 디자인 원본은 클릭 즉시 처리(확인 다이얼로그 없음, `onClick={()=>{...}}`
   생략). 파괴적 액션인데 확인 단계 없이 바로 서버 호출할지, `window.confirm` 등 최소 확인을 넣을지
   브리프에 명시 없음 — 기존 재사용 선례(`ReturnListCard`의 "반납 처리"도 확인 없이 즉시 처리)를
   따르면 확인 없음이 관례에 가깝지만 확정 필요.
3-1. 위와 별개로 두 버튼을 하나의 `renderCell` 셀 안에서 `gap-1.5`(디자인 원본 `gap:6`) 정도로
   배치하는 것은 확정(디자인 원본 그대로), 이견 없음.
4. **상태 변경 셀의 `width`**: 디자인 원본은 `22%`(4컬럼 합 90%, 잔여 10%는 `table-auto`가 분배).
   기존 `BOOK_COLUMNS`/`RETURN_COLUMNS` 관례상 폭 합계를 100% 미만으로 두고 잔여를 표가 분배하게
   두는 패턴이므로 그대로 따를 수 있으나, 정확한 %는 architect가 최종 확정.
5. **Toast/refreshToken 소유 주체**: `CopyListCard`가 자체 Toast를 갖고 refetch만 하는지(= 등록
   폼과 별개 재조회 트리거), 아니면 `CopyRegisterSection`의 `refreshToken`(등록 성공 시 목록 갱신용)과
   "상태 변경 성공 시 재조회"가 같은 트리거를 공유할지 별개로 둘지 — `BookRegisterSection` 선례는
   폼→목록 단방향 refreshToken만 다루고, 목록 자체 행위(상태 변경)로 인한 재조회는 다루지 않아
   참조 선례가 정확히 일치하지 않음. component-architect 판단 필요.
6. **관리번호/도서명 검색 Input의 `aria-label`/`label` 표시 여부**: `ReturnListCard`는 `aria-label`만
   쓰고 시각 라벨 없이 `placeholder`로 대체했다. 이 화면도 동일하게 갈지, 두 입력이 나란히 있어
   구분을 위해 시각 라벨(`label` prop)을 쓸지 확인 필요.
