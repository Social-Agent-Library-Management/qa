## 상태/상호작용
- 대여일 변경 → 반납예정일 미리보기가 즉시 재계산(+14일). 서버 응답의 `dueDate`가 최종 진실이지만, 제출 전 미리보기는 프론트에서 계산.
- 초기화: 디자인 원본은 대여일만 오늘로 되돌리지만, 이 코드베이스의 자매 폼(`CopyRegisterForm`)은 전체 필드를 리셋하는 컨벤션이 확립돼 있음 → **전체 필드 리셋**으로 통일(일관성 우선, 디자인 사소한 편차는 기존 패턴을 따름).
- 등록 성공 → 폼 초기화 + Toast + 목록(현재 대출 현황) 재조회.
- 목록은 실시간 반영이 필요하므로 서버 페이지네이션(`BookListCard`와 동일 패턴)으로 조회, `refreshToken`으로 등록 성공 시 재조회.

## 반응형
- 기존 화면(`copies/new`, `books/new`)과 동일하게 데스크톱 그리드 2열 → 모바일 1열(`grid-cols-1 sm:grid-cols-2`, 기존 폼들과 동일 클래스 사용).

## 중복 후보 → 재사용 판정 (백엔드 API 대조 완료)
| 요소 | 판정 |
|---|---|
| PageHeader, Card, Input(+Field), Button, DataTable, Badge/StatusBadge, Toast | 기존 `ui/`, `library/status-badge` 그대로 재사용 |
| 폼 카드 + 목록 카드 조합·refreshToken 배선 | `BookRegisterForm`+`BookListCard`+`BookRegisterSection` 3분할 패턴을 그대로 따름 |
| 관리번호 입력 | **plain `Input`** (Combobox 아님). 이유: 백엔드 `BookItemRepository`에 관리번호 검색/목록 API가 없음(`findByManagementNumber`만 존재, 컨트롤러에 GET 없음) — 디자인 원본도 plain input이라 스펙과 API 둘 다 일치. `components/README.md`의 "`/loans/new`의 소장본·회원 선택이 Combobox 경로를 쓴다"는 기존 메모는 **API 부재로 틀린 예측** → 이번 구현에서 정정(관리번호는 서버 검증 에러(`BOOK_ITEM_NOT_FOUND`/`BOOK_ITEM_NOT_AVAILABLE`)로 필드 에러 처리). |
| 대출자/부서 | 백엔드에 "회원" 도메인 자체가 없음(자유 텍스트 `borrowerName`/`department`) → 검색형 선택 불필요, plain `Input` 2개 |

## 백엔드 API 계약 (Kotlin 직접 조사)
- `POST /loans` — `CreateLoanService.Request{ managementNumber, borrowerName, department, loanDate(LocalDate), borrowerEmail? }` → 201 `Response{ loanId, bookItemId, managementNumber, bookTitle, borrowerName, department, borrowerEmail, loanDate, dueDate, status }`. 디자인에 이메일 입력은 없음 → 프론트에서 생략(옵셔널이라 안 보내도 됨).
- 에러: `BOOK_ITEM_NOT_FOUND`(404), `BOOK_ITEM_NOT_AVAILABLE`(409) — `LoanError.kt`. `CopyRegisterForm`과 동일하게 필드 에러로 매핑(토스트 아님).
- `GET /loans?status=ON_LOAN&page&pageSize` — `SearchLoansService.Response{ loans: LoanSummary[], pagination }`. `LoanSummary`에 `overdue: Boolean` 파생 필드 포함(서버가 계산) → 상태 뱃지에 활용.
- `dueDate = loanDate + 14일`(`Loan.LOAN_PERIOD_DAYS`) — 프론트 미리보기 계산도 14로 고정(매직넘버 아님, 서버 상수와 동일 의미로 주석 처리).
