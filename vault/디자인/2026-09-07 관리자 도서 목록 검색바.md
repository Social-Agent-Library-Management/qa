# 디자인 스펙: 관리자 도서 등록 화면 — "등록된 도서 목록" 검색바 추가

## 개요
관리자 도서 등록 화면(`/admin/books/new`)의 "등록된 도서 목록" 카드에 검색 입력을 추가하는 **범위가 좁은 변경**이다. 화면 전체를 새로 만들지 않는다. Claude Design 원본(`ui_kits/library/index.html`, `BookRegistrationScreen` L222-255 + `SearchInput` L116-126)은 검색바를 별도 카드로 두지 않고, 기존 "등록된 도서 목록" `Card`(`noPadding`) 내부 최상단에 얇은 헤더 행으로 끼워 넣은 뒤 그 아래 `DataTable`을 이어 붙인다. 입력값은 도서명·저자·출판사·ISBN 통합 검색으로 쓰이며, 디자인은 클라이언트 `Array.filter` 목업이지만 실제 구현은 이미 `q` 파라미터를 지원하는 `/books/search` API(`searchBooks`)를 호출해야 한다. 등록 폼(`BookRegisterForm`)과 페이지 레이아웃은 이번 변경 대상이 아니다.

## 레이아웃 트리
디자인 원문(`BookRegistrationScreen`) 기준. 취소선 없이 표시된 항목만 이번 변경 대상이고, 나머지는 기존 그대로(변경 없음)다.

```
BookRegistrationScreen (padding: 32px 40px)
├─ PageHeader (title="도서 등록") — 변경 없음
├─ Card "새 도서 등록" (marginBottom:20) — 변경 없음, 등록 폼 그대로
└─ Card "등록된 도서 목록" (noPadding, titleRight=CountBadge)
   ├─ [신규] 검색 헤더 행 — Card 헤더(제목 바) 바로 아래, DataTable 위
   │  └─ SearchInput (아이콘 + placeholder="도서명, 저자, 출판사 또는 ISBN으로 검색")
   └─ DataTable (columns: 도서명/저자/출판사/ISBN/소장본 수, pageSize=20,
       emptyText="검색 결과가 없습니다.") — 컬럼·페이지네이션 구조는 변경 없음,
       바인딩되는 rows/total만 검색 반영
Toast (등록 성공 시) — 변경 없음
```

**주의 — 배치 위치 정정:** 디자인 JSX 상 검색 헤더 행(`padding:14px 20px; border-bottom:1px solid var(--color-border)`)은 `Card`의 `children`(즉 `noPadding` 본문) 맨 앞 요소다. `Card`가 자체 타이틀 바(`title="등록된 도서 목록"` + `titleRight`)를 이미 그리므로, 실제 렌더 순서는 **Card 타이틀 바 → 검색 헤더 행(구분선 포함) → DataTable** 3단이 된다. Card 타이틀 바 자체를 검색바로 대체하는 게 아니다.

## 디자인 토큰
신규 토큰 없음. 전부 이슈 #31 스펙에서 이미 확인된 기존 `@theme` 토큰에 매핑된다(`src/app/globals.css`).

| 디자인 원문 값 | 프로젝트 토큰 | Tailwind 유틸 |
|---|---|---|
| `border:1px solid var(--color-border)` | `--color-line` | `border border-line` |
| 검색 헤더 행 `borderBottom:1px solid var(--color-border)` | `--color-line` | `border-b border-line` |
| `background:var(--color-bg)` (SearchInput 내부 input) | 참고용 — 실제 재사용 `Input`은 `bg-surface`를 쓰고 있음(기존 결정, 이번에 바꾸지 않음) | `bg-surface`(기존) |
| `color:var(--color-text-primary)` | `--color-fg` (원본 명칭이 `text-*`이지만 프로젝트 `text-primary`는 브랜드색이라 별도 매핑됨 — #31에서 이미 정정됨) | `text-fg`(기존 `Input`이 이미 적용) |
| `borderRadius:8` | `--radius-input` | `rounded-input`(기존 `Input`이 이미 적용) |
| `height:40` | 기존 `Input` 높이 토큰(`h-11`=44px, cva 기본값) | 기존 `Input` 그대로 — 디자인 40px과 소폭 차이 있으나 이번 작업에서 새 높이 variant를 만들지 않는다(아래 미확정 항목 참고) |
| 검색 헤더 행 패딩 `14px 20px` | 4px 그리드 표준 스케일 | `py-3.5 px-5` (14px/20px, Tailwind 기본 스케일과 일치) |
| placeholder 아이콘 좌측 오프셋 36px | `Input`의 `hasLeadingIcon` variant가 이미 `pl-9`(36px)로 흡수 | 기존 `Input leadingIcon` 그대로 |

## 컴포넌트 인벤토리

| 컴포넌트 | 설명 | 반복 | 중복 후보 | 비고 |
|---|---|---|---|---|
| 디자인 `SearchInput` (아이콘+테두리+radius 8+bg) | 검색 입력 | 1(이 화면 기준) | **아니오 — 기존 코드에 동일 시각 컴포넌트 존재** | `src/components/ui/input.tsx`의 `Input`(`leadingIcon` prop)과 시각적으로 동일. `/books/search` 화면(`BookSearchSection`)이 이미 `<Input leadingIcon={<IconSearch size={16}/>} .../>`로 이 스타일을 구현해 씀. **신규 시각 컴포넌트를 만들 필요가 없다** — 이것이 이 스펙의 핵심 재사용 판단이며, 최종 결정은 component-architect가 하되 검토 낭비 없이 "기존 `Input` 재사용"으로 시작할 것을 권고한다. |
| 검색 헤더 행(래퍼 `div`) | Card 본문 최상단, 구분선 있는 얇은 행 | 1 | 아니오 | 새 공용 컴포넌트가 아니라 `BookListCard` 내부의 레이아웃용 `div`(`border-b border-line py-3.5 px-5`)로 충분해 보임 — 최종 판단은 architect. |
| `Card`(`noPadding`) | "등록된 도서 목록" 컨테이너 | 1 | 아니오 | 기존 컴포넌트, 변경 없음. |
| `DataTable` | 목록 표 | 1 | 아니오 | 기존 컴포넌트, 변경 없음. 바인딩 데이터만 검색 반영. |
| `IconSearch` | 검색 아이콘 | 1 | 아니오 | 기존 아이콘, 재사용(`src/components/icons`). |
| `useDebouncedValue` | 입력 디바운스 훅 | 1 | 아니오 | 기존 훅, 재사용(`src/lib/use-debounced-value.ts`, 기본 250ms). |

**참조 선례 (신규 구현 아님, 패턴만 복제):** `BookSearchResultCard`(`src/components/library/book-search-result-card.tsx`)가 `query` prop → `useDebouncedValue(query)` → `q !== prevQuery`면 1페이지 복귀 → `searchBooks({ q, page, pageSize })` 패턴을 이미 완전히 구현해 두었다. 이번 변경(`BookListCard`)의 1차 참조 구현이다. 단 `BookSearchResultCard`는 검색어를 부모(`BookSearchSection`)가 소유하고 행 선택·오타 제안 기능이 있다 — 이번 대상(`BookListCard`)은 디자인에 그 기능이 없으므로 가져오지 않는다(범위 제외, 아래 "미확정 항목" 아님 — 명시적 제외).

## 상태 & 상호작용

| 요소 | 상태/동작 | 근거 |
|---|---|---|
| 검색 입력 | 타이핑 → 로컬 state 즉시 갱신(입력 지연 없이 화면에 반영) | 디자인 `value={search} onChange={...}` — 확인됨 |
| 검색 입력 → API 호출 | 값이 바뀌면 디바운스(250ms, `useDebouncedValue` 기본값) 후 `q`로 재조회 | 디자인은 즉시 클라이언트 filter지만, 실제 구현은 서버 API이므로 참조 선례(`BookSearchResultCard`)의 디바운스 패턴을 따른다 — 프로토타입-실구현 간극, 명시적으로 이 스펙에 기록 |
| 검색어 변경 시 페이지네이션 | 1페이지로 복귀 | 참조 선례(`BookSearchResultCard`)와 동일 패턴 — 서버 페이지네이션에서 검색어가 바뀌면 이전 페이지 번호가 무의미해짐 |
| 등록 성공(`refreshToken` 증가) 시 검색어 | 미확정 — 디자인에 해당 시나리오 없음 | 아래 "미확정 항목" 참고 |
| 검색 결과 0건 | `DataTable emptyText="검색 결과가 없습니다."` | 디자인 원문에 하드코딩됨(검색 여부 무관하게 항상 이 문구) |
| 로딩 상태 | 기존 `BookListCard`의 "요청 키 vs 완료 키" 파생 패턴을 그대로 따름(변경 없음) | 기존 코드 확인 |
| 에러 상태 | 기존 `ListErrorState` + 재시도(변경 없음) | 기존 코드 확인 |
| hover/focus/disabled (입력 자체) | 미확정 — 디자인 원문에 명시 없음, 기존 재사용 `Input`의 기본 스타일을 그대로 따르면 될 것으로 추정 | 스크린샷/상태 스펙 없음 |
| 검색 입력 접근성 라벨(`aria-label`) | 미확정 — 디자인 원문은 `placeholder`만 지정, `aria-label` 없음. 참조 선례는 `aria-label`을 별도로 채움 | 확인 필요 |

## 반응형 규칙
디자인 원문(`BookRegistrationScreen`, `SearchInput`)에 브레이크포인트 분기 코드 없음. 검색 헤더 행은 `flex:1`(SearchInput의 `position:relative;flex:1`)로, 폭이 있는 한 줄 레이아웃을 전제로 한다 — 별도 반응형 규칙 없음(미확정, 필요시 참조 선례인 `BookSearchSection`의 `flex flex-col gap-2.5 sm:flex-row` 모바일 스택 패턴을 참고할 수 있으나 디자인에 명시된 요구는 아니다).

## 데이터/콘텐츠 형태
- 검색어: `string` (로컬 state, 빈 문자열 = 전체 조회)
- API 요청: `searchBooks({ q, page, pageSize }, signal)` — `src/lib/api/books.ts`에 이미 구현·확인됨. `BookListCard`는 현재 `q`를 넘기지 않으므로 이를 연결하는 것이 이번 작업의 핵심.
- API 응답: 기존 `BookSearchResult`/`BookListItem` 타입 그대로(변경 없음) — `{ books: BookListItem[]; pagination: { totalElements, ... } }`
- `SearchInput` props(디자인 원문 기준, 실제 구현은 재사용 `Input`으로 대체): `{ value: string; onChange: (e) => void; placeholder?: string }`

## 미확정 항목 (확인 필요)
1. **입력 높이 불일치(40px vs 기존 `Input` 44px):** 디자인 `SearchInput`은 `height:40`, 프로젝트 기존 `Input`은 `h-11`(44px, cva 기본). 이번 작업에서 새 높이 variant를 만들지, 기존 `Input` 기본 높이를 그대로 쓸지 architect/implementer 판단 필요. (참조 선례 `BookSearchSection`도 기존 `Input` 기본 높이를 그대로 쓰고 있어 선례를 따르는 쪽이 일관적일 수 있음 — 다만 결정은 이 스펙의 역할이 아니라 다음 단계로 넘김.)
2. **`refreshToken`(등록 성공) 발생 시 검색어 유지 여부:** 디자인 원문에 이 상호작용이 없음. 도서 등록 후 검색어를 초기화할지, 유지한 채 재조회할지 확인 필요.
3. **검색 입력 `aria-label`:** 디자인 원문에 없음. 참조 선례(`BookSearchSection`)는 `aria-label="도서명, 저자, 출판사, ISBN 검색"`을 명시적으로 채움 — 문구를 이번 placeholder("도서명, 저자, 출판사 또는 ISBN으로 검색")에 맞출지, 선례 문구를 그대로 쓸지 확인 필요.
4. **빈 상태 문구 조건:** 디자인은 검색 여부와 무관하게 항상 `emptyText="검색 결과가 없습니다."`를 쓴다. 등록된 도서가 아예 0건인 경우(검색어 없이도 0건)에도 이 문구를 쓸지, 기존 기본 문구("데이터가 없습니다.")와 분기할지 확인 필요.
5. **검색 헤더 행 초기화 버튼 유무:** 디자인 `SearchInput`에는 초기화(clear) 버튼이 없음. 참조 선례(`BookSearchSection`)는 별도 "초기화" `Button`을 둔다. 디자인에 없으므로 기본값은 "추가하지 않음"이나, 최종 확인 필요.

## 결정 사항 (오케스트레이터 확정 — 아래 5건은 architect/implementer가 재검토하지 말고 그대로 따를 것)

1. **입력 높이:** 새 variant 만들지 않는다. 기존 `Input` 기본 높이(`h-11`, 44px) 그대로 쓴다. 참조 선례(`BookSearchSection`)와 동일 — 디자인 40px과의 소폭 차이는 무시(#31 선례: 신규 토큰/variant 없이 기존 값에 흡수).
2. **`refreshToken` 발생 시 검색어:** 유지한다(초기화하지 않는다). `BookListCard`가 검색어를 자체 소유하므로 `refreshToken`은 기존 로직(1페이지 복귀)만 그대로 두고, 검색어를 지우는 코드를 추가하지 않는다 — 별도 배선 없이 "손대지 않는 것"이 결정이다.
3. **`aria-label`:** placeholder와 동일 문구로 채운다 — `aria-label="도서명, 저자, 출판사 또는 ISBN으로 검색"`.
4. **빈 상태 문구:** 검색 여부와 무관하게 항상 `emptyText="검색 결과가 없습니다."`(디자인 원문 그대로, 분기 없음). 현재 `BookListCard`는 `emptyText`를 안 넘겨 `DataTable` 기본값("데이터가 없습니다.")을 쓰고 있었는데, 이번에 명시적으로 넘기도록 바꾼다.
5. **초기화(clear) 버튼:** 추가하지 않는다. 디자인에 없다 — 범위 밖.
