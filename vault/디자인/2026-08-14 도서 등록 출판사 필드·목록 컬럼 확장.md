# 디자인 스펙: 도서 등록 화면 — 출판사 필드 + 출판사 소장본 수 조회 + 목록 컬럼 확장

## 개요

기존 "도서 등록" 화면(`src/app/books/new/page.tsx` → `BookRegisterSection` → `BookRegisterForm` + `BookListCard`)을 확장하는 작업이다. Claude Design의 `BookRegistrationScreen`(디자인 URL 대신 `_workspace/00_input/brief.md`에 발췌된 JSX로 확인됨)은 등록 폼에 출판사 입력을 포함하고, 목록 표에 출판사·소장본 수 컬럼을 이미 갖고 있다 — 즉 기존 프론트가 디자인 대비 누락돼 있던 상태다. 여기에 더해 디자인에는 없는 신규 기능인 **"출판사 소장본 수 조회"**(출판사명을 입력하면 그 출판사가 이미 보유한 소장본 수를 디바운스 조회해 보여주는 안내)를 추가한다. 백엔드에 전용 조회 엔드포인트가 없으므로, 이 기능은 `/books/search`를 페이지 워크하며 클라이언트에서 완전일치 필터링·집계하는 방식으로 구현된다(리더 확정 사항, 이 스펙은 그 결정을 그대로 반영).

이 스펙은 기존 프론트 코드(`book-register-form.tsx`, `book-list-card.tsx`, `book-register-section.tsx`, `lib/api/books.ts`, `lib/use-debounced-value.ts`, `book-select-field.tsx`, `loan-register-form.tsx`, `loan-history-card.tsx`, `globals.css`, `ui/data-table.tsx`, `ui/card.tsx`, `ui/badge.tsx`, `ui/input.tsx`)를 직접 읽고 확인한 내용을 기반으로 한다. PageHeader는 스코프 밖(기존 공용 셸이 이미 담당)이라 아래 레이아웃 트리는 페이지 본문(`BookRegisterSection`)부터 시작한다.

## 레이아웃 트리

```
BookRegisterSection (client 경계, 기존 — 변경 없음)
├─ BookRegisterForm  (Card: title="새 도서 등록", titleAs="h2")  ── 변경
│  └─ <form>
│     ├─ 필드 그리드 (div.grid grid-cols-1 sm:grid-cols-2 gap-x-6 gap-y-4) ── 3→4개로 확장
│     │  ├─ Input 도서명 (label="도서명", required)                      [기존]
│     │  ├─ Input 저자   (label="저자", required)                        [기존]
│     │  ├─ Input 출판사 (label="출판사", required)                      [신규]
│     │  └─ Input ISBN   (label="ISBN", hint="13자리 ISBN을 입력하세요")  [기존, 순서상 4번째로 유지]
│     ├─ 출판사 소장본 수 안내 박스 (조건부 렌더 — 아래 "신규 기능 스펙" 참조) [신규]
│     ├─ 액션 영역 (div.flex justify-end gap-2 mt-5)                    [기존]
│     │  ├─ Button 초기화 (variant="ghost")
│     │  └─ Button 등록   (variant="primary", type="submit")
│     └─ Toast (성공/실패 안내)                                          [기존]
│
└─ BookListCard  (Card: title="등록된 도서 목록", noPadding, titleRight=Badge)  ── 변경
   ├─ Card titleRight: Badge(variant="soft", tone="neutral") "{total}건"  [기존]
   └─ DataTable<BookListItem>
      └─ columns × 5 (기존 3 → 5)  [변경]
         1. title   (도서명)
         2. author  (저자)
         3. publisher (출판사, secondary)         [신규]
         4. isbn    (ISBN, secondary, nowrap)      [기존]
         5. bookItemCount (소장본 수)              [신규]
```

디자인 JSX의 필드 순서(도서명 → 저자 → 출판사 → ISBN)와 현재 프론트의 필드 순서(도서명 → 저자 → ISBN)를 비교하면, **출판사는 ISBN 앞(3번째)에 삽입**해야 디자인과 일치한다. 2×2 그리드에서는 1행 "도서명/저자", 2행 "출판사/ISBN"이 된다.

**component-architect에게 가장 중요한 신호**: 안내 박스 패턴이 이번 작업으로 **2회째** 등장한다. 프로젝트는 디바운스 로직을 정확히 이 "2회째 반복" 시점에 `lib/use-debounced-value.ts`로 승격시킨 전례가 있다(`BookSelectField` → `LoanHistoryCard`). 안내 박스도 같은 전례를 따를 후보다.

## 상태 & 상호작용

### 1. 폼 제출 (등록 버튼)
- `required` 네이티브 검증: 도서명, 저자, **출판사**(신규 추가) — ISBN은 선택.
- 제출 시 `createBook({ title: trim, author: trim, publisher: trim, isbn: trim || null })` 호출.
- 성공: 폼 전체 초기화(출판사 포함), `Toast(tone="success", "도서가 등록되었습니다.")`, `onCreated?.(book)` → `BookRegisterSection`의 `refreshToken` 증가 → `BookListCard` 재조회(기존 배선 그대로, 변경 불필요).
- 실패:
  - `409 DUPLICATE_ISBN` → 기존 패턴 그대로 ISBN 필드 에러(`isbnError`)로만 표시, 토스트 없음.
  - 그 외 → `Toast(tone="danger", error.detail 또는 fallback 문구)`.
  - 출판사 자체에 대한 백엔드 필드 에러는 계약상 없음(`required`가 blank 제출 자체를 막으므로 사실상 도달 불가) — 도달 시에도 일반 토스트 폴백으로 처리.

### 2. 초기화 버튼
- 4개 필드 전부(출판사 포함) 빈 값으로 리셋, `isbnError` 초기화.
- 출판사 값이 빈 문자열이 되면 안내 박스는 "미입력" 상태로 자연히 사라진다(별도 리셋 로직 불필요 — 박스 가시성이 출판사 입력값에서 파생되므로).

### 3. 출판사 입력 → 소장본 수 조회 (신규)
- 트리거 조건: `publisher.trim().length >= 2` (브리프 예시 임계치).
- 디바운스: `useDebouncedValue(publisher, 350)` — 필드별 개별 호출 원칙 준수(객체로 묶지 않음). 350ms는 브리프가 제시한 "300~400ms" 범위의 중간값 제안.
- 가시성(박스 렌더 여부)은 **디바운스되지 않은 원본** `publisher.trim().length` 기준으로 즉시 판단(사용자가 빠르게 지웠을 때 박스가 늦게 사라지는 지연 방지). 조회 자체(API 호출)만 디바운스된 값을 쓴다.
- 요청: `getPublisherItemCount(debouncedPublisher.trim(), signal)` — `BookListCard`/`BookSelectField`와 동일한 "요청 키 vs 완료 키(settled)" 패턴으로 로딩/경합을 파생시킨다. `AbortController`로 이전 요청 취소(기존 패턴 그대로, 재발명 금지).
- 실패 시 토스트 없음(타이핑 방해 금지 — `BookSelectField`의 `searchError` 처리와 동일 원칙), 박스 내부에 국소 표시.

**상태표**:

| 상태 | 조건 | 값 영역 표시 | 톤 |
|------|------|------------|-----|
| 미입력 | `publisher.trim().length < 2` | 박스 자체를 렌더하지 않음 | — |
| 로딩 | 임계치 이상 + 디바운스 대기/요청 진행 중 | "조회 중…" | `text-fg-muted` (비강조) |
| 0건(신규 출판사) | 요청 성공, 완전일치 0건 | "등록된 소장본 없음" | `text-fg-muted` (에러 아님을 명확히 — 신규 출판사는 정상 케이스) |
| N건 | 요청 성공, 1건 이상 | `"{itemCount}권"`(주), 필요 시 `"(도서 {bookCount}종)"` 보조 | `text-primary font-semibold`(주 값) |
| 조회 실패 | 네트워크/서버 에러 | "확인하지 못했습니다" | `text-fg-muted`, 토스트 없음 |

박스 마크업(제안 — `LoanRegisterForm`의 반납예정일 박스와 동일 골격, `aria-live="polite"`로 스크린리더에 상태 변화 통지):

```
<div className="mt-4 flex items-center gap-2.5 rounded-md bg-primary-light px-3.5 py-3" aria-live="polite">
  <IconBook className="text-primary shrink-0" aria-hidden="true" />
  <span className="text-base leading-cozy tracking-normal text-fg-muted">
    "{publisher}" 출판사의 등록된 소장본
  </span>
  <strong className="ml-auto text-body leading-cozy font-semibold tracking-normal {상태별 톤}">
    {상태별 값}
  </strong>
</div>
```

일치 판정 규칙(브리프 확정 사항 재확인): `book.publisher.trim().toLowerCase() === 입력값.trim().toLowerCase()` — **완전 일치**만 집계한다(부분 일치 아님).

### 4. 도서 목록 표
- 로딩/에러/재시도/빈 상태: 기존 그대로(변경 없음) — `DataTable`의 `loading`/`emptyText`, `BookListCard`의 에러 재시도 버튼.
- ISBN `null`/빈 값 → `"—"` 렌더(기존 `renderCell` 로직 유지). 출판사는 백엔드 계약상 non-blank 필수라 `null` 케이스 없음(확인됨) — 동일한 `"—"` 폴백은 불필요.
- `refreshToken` 변경 시 1페이지로 복귀하는 기존 로직 무변경 — 컬럼이 늘어나는 것과 무관.

### 5. 인터랙션 상태(hover/focus/disabled)
- 출판사 `Input`: 기존 `Input`의 `focus:border-primary focus:shadow-focus-ring`, `disabled:opacity-55`가 그대로 적용(신규 스타일 불필요).
- 제출 중(`submitting`): 기존과 동일하게 두 버튼 `disabled`, 등록 버튼 `aria-busy` + "등록 중…" 텍스트.

## 반응형 규칙

브레이크포인트는 Tailwind 기본값(`sm`=640px)만 쓴다 — 이 프로젝트에 커스텀 브레이크포인트 토큰 없음(확인됨, `globals.css`에 브레이크포인트 정의 없음).

- **base(<640px)**: 필드 그리드 `grid-cols-1` — 도서명/저자/출판사/ISBN이 세로 4행으로 스택(순서 그대로). 안내 박스는 전체 폭 `flex` 행 유지, 라벨이 길면 줄바꿈 가능(`LoanRegisterForm` 박스와 동일 처리 — 별도 대응 불필요). 목록 표는 `overflow-x-auto`로 가로 스크롤(기존 3컬럼 때도 동일 원칙, 5컬럼이라 스크롤 폭만 늘어남).
- **sm 이상(≥640px)**: 필드 그리드 `grid-cols-2` — 1행(도서명/저자), 2행(출판사/ISBN)의 2×2 배치. 디자인의 `Grid2`(2열) 의도와 일치.
- Card·버튼 영역 레이아웃은 브레이크포인트 무관 변경 없음.

## 데이터/콘텐츠 형태

백엔드 계약(`src/main/kotlin/org/library/book/`, 리더 조사분) 기준.

```ts
// src/lib/api/books.ts — 변경

export type BookListItem = {
  id: number;
  title: string;
  author: string;
  publisher: string;        // 신규 — non-blank (백엔드 Book 도메인 제약)
  isbn: string | null;
  bookItemCount: number;    // 신규 — 활성(soft-delete 제외) 소장본 집계, BookDocument에 이미 포함
};

export type Book = BookListItem & {
  createdAt: string; // LocalDateTime
};

export type CreateBookInput = {
  title: string;
  author: string;
  publisher: string;        // 신규, 필수 (POST /books 계약)
  isbn?: string | null;
};

// 기존 SearchBooksParams/BookSearchResult 구조는 변경 없음 —
// q는 title/author만 대상(publisher는 검색 파라미터 아님, 확인됨).
```

신규 조회 함수(정확한 이름/파일 위치는 architect 확정 — 아래는 shape 제안):

```ts
export type PublisherItemCountResult = {
  bookCount: number;   // 완전일치한 도서 종수
  itemCount: number;   // 그 도서들의 bookItemCount 합산
};

// 내부 동작(리더 확정):
// searchBooks({ page, pageSize: 100 }, signal)를 q 없이 페이지 워크(1페이지부터
// totalElements를 다 채울 때까지) 하며 books를 순회, publisher가 trim 후
// 대소문자 무시 완전일치하는 행만 걸러 bookCount/itemCount를 누적한다.
// signal은 모든 하위 searchBooks 호출에 전달하고, abort 시 루프를 즉시 중단한다.
function getPublisherItemCount(
  publisher: string,
  signal?: AbortSignal,
): Promise<PublisherItemCountResult>;
```

이 함수는 기존 `lib/api/books.ts`의 다른 함수들(단발 fetch 1회)과 달리 **여러 페이지를 순회하는 루프**라는 점이 구조적으로 다르다 — architect가 재사용/캡슐화 방식을 판단할 때 이 차이를 고려해야 한다.

DataTable 컬럼 정의(디자인 JSX `cols` 배열을 그대로 인용, `key`만 프론트 타입에 맞춰 `copies`→`bookItemCount`로 교정):

```ts
const BOOK_COLUMNS: DataTableColumn<BookListItem>[] = [
  { key: "title", label: "도서명", width: "28%" },
  { key: "author", label: "저자", width: "14%" },
  { key: "publisher", label: "출판사", width: "16%", secondary: true },
```

폭 합계가 88%로 100%가 안 되지만(`table-auto` + 브라우저가 나머지 폭을 자동 분배), 디자인 JSX 원본 값을 그대로 인용한 것— 임의로 재조정하지 않았다(사실과 추측 구분 원칙).

## 미확정 항목

1. **안내박스 정확한 카피**: 라벨 문구("{publisher} 출판사의 등록된 소장본" 등), 단위("권" vs 다른 표기), `bookCount` 보조 표기 노출 여부 — 위 제안은 디자인 언어(반납예정일 박스)에서 유추한 것이지 디자인 원본에 확정된 문구가 아니다. 확인 필요.
2. **목록 표 "소장본 수" 셀 포맷**: 순수 숫자만 렌더할지("3") 단위를 붙일지("3권") — 디자인 JSX 발췌에는 `cols` 정의만 있고 셀 렌더링/포맷 코드는 없어 확인 불가.
3. **`getPublisherItemCount`의 전체 페이지 워크 성능**: 도서 수가 늘어나면 매 디바운스 조회마다 전체 카탈로그를 여러 페이지에 걸쳐 훑는 비용이 커진다. 백엔드 전용 엔드포인트 부재가 전제인 임시방편이며, 장기적으로는 백엔드 이슈 분리가 필요할 수 있음 — 이번 스코프 밖, 리더 확인 필요.
4. **출판사 필드의 자동완성/선택 UI 필요 여부**: 브리프는 완전일치 집계 "조회"만 요구했고 `BookSelectField`류 Combobox(기존 출판사 목록에서 선택) 요구는 없었다. 이 스펙은 plain `Input` + 안내박스로 한정했다 — 만약 자동완성까지 필요하다면 별도 확인 필요.
5. **조회 실패 시 재시도 UI 제공 여부**: 브리프에 명시 없음. 이 스펙은 "재시도 버튼 없음, 다음 타이핑 시 자동 재요청"으로 가정했다.
6. **안내박스 아이콘으로 `IconBook` 사용**: 인터프리터 제안(기존 아이콘 재사용, `IconCalendar`와 대응하는 역할)이며 디자인 원본에 명시된 아이콘은 아니다.
7. **안내박스 공용 컴포넌트 추출 여부/이름**: 컴포넌트 인벤토리에서 "2회 반복 — 중복 후보"로 표시했으나, 최종 추출 여부·props API·파일 위치는 component-architect의 판단 영역이다(이 스펙은 시각/상태 명세까지만 담당).
