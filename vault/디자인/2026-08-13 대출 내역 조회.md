# 01. 디자인 스펙 — 대출 내역 조회 (`LoanHistoryScreen`)

소스: Claude Design `307f4357-35a5-463d-9674-9b2fefff09fa`, `ui_kits/library/index.html`, `LoanHistoryScreen` 컴포넌트(JSX 발췌).
백엔드 대조: `/Users/chanyoung/Desktop/library/src/main/kotlin/org/library/loan/`(`GET /loans`). 원문·API 조사는 `00_input/design-note.md`, `00_input/api-notes.md` 참조.
이슈: `#15`. 기존 구현 참고: `LoanListCard`(`#11`, 서버 페이지네이션 패턴), `ReturnListCard`(`#13`, fetch-all 클라이언트 필터 패턴 — 이 화면은 **이 패턴을 쓰지 않는다**).

## 개요

대출 이력 전체(대출 중 + 반납 완료)를 검색·조회하는 화면. 행동 버튼이 없는 **조회 전용**이며, 반납 완료 건까지 누적되므로 시간이 지날수록 데이터가 무한정 늘어난다. 디자인 원본은 통합 검색창 1개(도서명·대출자·관리번호 OR 검색) + 상태 select(전체/대출중/연체/반납완료) + 클라이언트 배열 필터를 전제로 만들어졌지만, 백엔드 `GET /loans`는 `bookTitle`/`borrowerName`/`department`/`status`(`ON_LOAN`|`RETURNED`)만 필터로 받고 관리번호 필터가 없으며 "연체"는 상태값이 아니라 행별 파생 불리언(`overdue`)이다. 이 스펙은 디자인의 시각적 톤(필터 바 + 표, 여백, 카드 구성)은 보존하되, 필터 UI와 페이지네이션 전략을 서버 계약에 맞게 재구성하는 방향을 명시한다.

디자인 원본 대비 구조적 차이:
- 검색 입력이 "통합 검색창 1개" → "개별 입력 3개(도서명/대출자/부서)"로 재구성됨(아래 컴포넌트 인벤토리 표 하단 근거 참조).
- `DataTable`의 `pageSize`(클라이언트 페이지네이션) 대신 `serverPagination`을 씀(`LoanListCard`와 동일 원칙, `ReturnListCard`와 다름) — 반납 완료 건까지 포함해 총량이 무한정 늘어나는 이력 화면이라 fetch-all이 성립하지 않기 때문.
- 액션 컬럼 없음(조회 전용) — `ReturnListCard`의 "반납 처리" 버튼 컬럼에 대응하는 요소가 이 화면엔 없다.

### 필터 UI 재구성 방향 (핵심 결정 — component-architect에게 우선 전달)

디자인 원본은 통합 검색창 1개(도서명·대출자·관리번호를 OR로 훑음)지만 다음 이유로 그대로 구현할 수 없다:

1. 서버는 `bookTitle`/`borrowerName`/`department`를 **서로 다른 파라미터**로 받는다 — 하나의 문자열을 세 필드에 OR로 서버 필터링할 방법이 없다(AND로 보내면 의미가 달라진다).
2. 클라이언트 fetch-all + 로컬 필터(`ReturnListCard` 패턴)로 우회할 수도 없다 — 이 화면은 반납 완료 건까지 포함한 전체 이력이라 총량이 시간이 지날수록 무한정 늘어난다. 진짜 서버 페이지네이션(`serverPagination`)이 필수이고, 서버 페이지네이션 위에서 클라이언트 필터를 얹으면 "페이지당 20건"이라는 표시와 실제 서버가 내려준 건수가 어긋난다.
3. 관리번호는애초 서버 필터 파라미터 자체가 없다.

→ **방향: 통합 검색창 1개를 "도서명 / 대출자 / 부서" 개별 입력 3개로 재구성한다.** 각각 서버 파라미터(`bookTitle`/`borrowerName`/`department`)에 1:1로 대응하는 AND 조합 검색이 된다(원본의 OR 통합 검색과 검색 의미론 자체가 달라짐 — 아래 상태&상호작용에 명시). 관리번호는 필터에서 제외하되(서버 미지원), **표의 관리번호 컬럼 자체는 유지**한다(눈으로 훑어 찾는 것은 가능).
필터 3개를 전부 넣을지, 사용 빈도가 낮을 "부서"를 접이식/2단 배치로 뺄지는 최종 UI 밀도 판단이라 component-architect가 결정한다 — 이 스펙은 "부서까지 포함한 3필드 개별 입력" 방향만 확정한다(서버가 지원하는 필터를 UI에서 임의로 누락시키지 않는다는 원칙).

### "연체" 상태 필터 처리 (핵심 결정)

디자인의 `StatusSelect`는 `전체`/`loaned`(대출중)/`overdue`(연체)/`returned`(반납완료) 4옵션이지만, 서버 `status` 파라미터는 `ON_LOAN`/`RETURNED` 2값뿐이고 "연체"는 각 행에 서버가 계산해 내려주는 파생 불리언(`overdue: boolean`)이다. 서버 페이지네이션 위에서 "연체만" 필터링하려면 서버가 `overdue` 기준 필터를 지원해야 하는데 현재 API엔 없다(클라이언트에서 추가로 걸러내면 페이지당 표시 건수가 서버가 말한 `pageSize`와 어긋난다 — `LoanListCard`/`ReturnListCard`가 지켜온 "서버가 확정한 상태만 신뢰" 원칙 위반).

→ **방향: 상태 필터에서 "연체" 옵션을 드롭한다.** 필터는 `전체`/`대출중`/`반납완료` 3옵션으로 축소. 단, **연체 배지 자체는 목록에서 사라지지 않는다** — 각 행은 여전히 `overdue` 필드를 받아 `status==='RETURNED' ? 'returned' : (overdue ? 'overdue' : 'loaned')`로 `StatusBadge`에 매핑한다(`LoanListCard`의 `toBadgeStatus`와 동일 로직). 즉 "대출중" 필터로 걸러진 결과 안에서도 연체 건은 빨간 배지로 시각적으로 구분되지만, "연체 건만 따로 걸러 보는" 기능은 이번 화면에서 제공하지 않는다. 이 트레이드오프는 스펙 결정 사항으로 남기고, 필요하면 후속 이슈로 서버 `overdue` 필터 파라미터 추가를 건의할 수 있음(이번 스코프 밖).

## 데이터/콘텐츠 형태

이 화면은 백엔드 `LoanSummary`(`src/lib/api/loans.ts`에 이미 정의됨)를 그대로 쓴다. 신규 타입 불필요.

```ts
// 이미 존재 — src/lib/api/loans.ts
type LoanSummary = {
  loanId: number;
  managementNumber: string;
  bookTitle: string;
  borrowerName: string;
  department: string;
  loanDate: string;      // "YYYY-MM-DD"
  dueDate: string;       // "YYYY-MM-DD"
  returnedAt: string | null;
  status: "ON_LOAN" | "RETURNED";
  overdue: boolean;      // 서버 계산 — 프론트 재계산 금지
};

type LoanSearchResult = {
  loans: LoanSummary[];
  pagination: { page: number; pageSize: number; totalPages: number; totalElements: number };
};
```

`SearchLoansParams`(현재 `status`/`page`/`pageSize`만 있음)는 **확장 필요** — `bookTitle`/`borrowerName`/`department` 세 파라미터를 추가해야 이 화면이 성립한다(`client.ts`의 쿼리 직렬화 패턴 재사용, 기존 필드는 유지 — `LoanListCard`/`LoanRegisterForm`이 계속 쓰는 필드를 건드리지 않는다). 이 확장은 component-architect/frontend-implementer 단계의 작업이며, 이 스펙은 "필요하다"는 사실과 방향만 명시한다.

`PageHeader`의 "총 N건"은 클라이언트 배열 길이(`all.length`, 디자인 원본 목업)가 아니라 서버 `pagination.totalElements`를 써야 한다 — 필터가 걸리면 "총 건수"의 의미가 "전체 이력 수"인지 "현재 필터 결과 수"인지 갈리는데, 서버가 필터된 결과의 `totalElements`를 내려주므로 **"현재 조회된(필터 적용) 결과 총 건수"**로 해석하는 것이 자연스럽다(이 화면은 필터 없는 디폴트가 곧 "전체 이력"이므로 필터 없을 때는 두 해석이 일치한다).

## 미확정 항목

1. **`Select`/`StatusSelect` 프리미티브 존재 여부** — `src/components/README.md` 인벤토리에 `Select` 계열 컴포넌트가 없다. 반납 처리/대출 등록 화면엔 상태 select가 없어(로컬 필터가 없거나 검색 input만 씀) 기존에 만들어진 적이 없을 가능성이 높다. component-architect가 `src/components/ui`를 재확인해 신규 프리미티브 필요 여부를 확정할 것.
2. **텍스트 필터 3개의 요청 트리거 방식** — 타이핑마다 서버 요청(디바운스 필요) vs Enter/검색 버튼 제출. 디자인 원본엔 명시 없음(클라이언트 필터라 트리거 개념 자체가 없었음). 확인 필요.
3. **부서 필터를 3개 입력에 포함할지, UI 밀도상 접거나 뺄지** — 스펙은 "3필드 방향"만 확정, 최종 배치는 아키텍트 판단.
4. **`LOAN_COLUMNS`/`toBadgeStatus` 공유 여부** — `LoanListCard`와 완전히 동일한 컬럼 정의·상태 매핑 로직이라 공용 모듈로 뺄지, 화면별로 유지할지 미확정(둘 다 도메인 합성 컴포넌트라 컴포넌트 설계 단계 판단 영역).
5. **`DataTable`의 가로 스크롤/모바일 대응 여부** — 기존 구현을 확인하지 않았다. 컬럼 7개가 좁은 화면에서 어떻게 처리되는지는 이미 `LoanListCard`/`ReturnListCard`가 겪은 문제라 기존 처리 방식을 그대로 따르면 됨(신규 결정 아님, 구현 단계에서 확인).
6. **결과 `Card`의 `title` prop 문구** — "대출 내역"으로 할지 비워둘지(디자인 원본은 `PageHeader`의 title="대출 내역 조회"와 결과 카드가 분리되어 있지 않았음, `noPadding` 카드에 별도 제목이 없었음). `LoanListCard`는 카드 자체 `title="현재 대출 현황"`을 쓰므로 이 화면도 일관성 있게 넣을지 결정 필요.
