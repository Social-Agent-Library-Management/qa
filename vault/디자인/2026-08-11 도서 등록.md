# 디자인 스펙: 도서 등록 (BookRegistrationScreen → `/books/new`)

입력 형태: **내보낸 JSX 코드**(`_workspace/00_input/design-url.md` 발췌, Claude Design 프로젝트 "도서 관리 시스템 Design System" `ui_kits/library/index.html`). 구조·컴포넌트명·props는 원문을 그대로 신뢰한다. 백엔드 API 계약(`_workspace/00_input/api-contract.md`)을 대조해 필드 스코프를 조정했다.

## 개요

도서를 신규 등록하는 화면이다. 상단에 페이지 제목, 그 아래 "새 도서 등록" 폼 카드(2열 그리드 입력 + 초기화/등록 버튼), 하단에 "등록된 도서 목록" 카드(건수 배지 + 페이지네이션 테이블)가 세로로 쌓인다. 등록 성공 시 하단 중앙에 토스트가 뜬다. **디자인 목업은 출판사·소장본 수 필드를 포함하지만, 백엔드 `POST /books` 계약에는 `title`/`author`/`isbn`만 존재한다 — 이 스펙은 시각적 레이아웃(2열 그리드, 카드 2개, 하단 테이블, 토스트)은 유지하되, 실제 구현 대상 필드는 API 기준으로 좁힌다.** 갭 상세는 "미확정 항목" 참조.

## 디자인 토큰

기존 `src/app/globals.css`의 `@theme` 토큰과 대조. 이 화면은 **신규 토큰이 필요 없다** — 전부 기존 토큰으로 표현 가능.

| 범주 | 디자인 값 | 대응 기존 토큰 | 비고 |
|------|----------|---------------|------|

## 상태 & 상호작용

| 요소 | 상태/동작 | 근거 |
|------|----------|------|
| Input(도서명) | `required`. 값 비어있으면 제출 시 브라우저 기본 검증(또는 폼 레벨 검증) 실패 | 디자인 원문 `required` + API `@NotBlank` |
| Input(저자) | `required`. 동일 | 디자인 원문 `required` + API `@NotBlank` |
| Input(ISBN) | 선택 입력(`required` 없음), `hint="13자리 ISBN을 입력하세요"` 상시 노출(에러 없을 때) | 디자인 원문 + API `isbn?: string \| null` |
| Input(ISBN) 에러 | 등록 시도 후 `409 CONFLICT`(`DUPLICATE_ISBN`) 응답을 받으면 ISBN 필드에 `error="이미 등록된 ISBN입니다."`를 세팅해 `hint` 대신 노출(테두리 danger로 전환) | `Input` 컴포넌트는 `error` prop이 있으면 자동으로 hint를 감추고 danger 스타일 적용. api-contract.md의 409 응답 `detail` 문구 그대로 사용 |
| Button(초기화) | 클릭 시 폼 전체를 빈 값으로 리셋(로컬 상태만, API 호출 없음) | 디자인 원문 `variant="ghost"`, 동작은 라벨 기반 추론 — **미확정: "값 원복" vs "빈 값 리셋" 중 어느 쪽인지 원문에 명시 없음, 빈 값 리셋으로 추정** |
| Button(등록) | 클릭 시 폼 검증(필수 필드) → `POST /books` 호출 → 성공 시 토스트 표시 + 폼 리셋 + 목록 갱신(재조회 또는 낙관적 추가) → 실패(409) 시 ISBN 필드 에러 표시, 토스트 없음 | 디자인 원문 `onClick={()=>setToast(true)}`은 항상 성공 가정 — 실제 구현은 API 응답 분기 필요(디자인이 다루지 않은 부분, 백엔드 계약 기준으로 보강) |
| Button(등록) 로딩 | 요청 중 버튼 `disabled` + 로딩 표시(스피너/문구) 권장 | **미확정 — 디자인 원문에 로딩 상태 없음.** `Button`이 이미 `disabled` prop을 지원하므로 구현 시 자연스럽게 추가 가능 |
| DataTable 행 | 클릭 동작 없음(원문에 `onRowClick` 미사용) | 디자인 원문에 행 클릭 핸들러 없음 |
| DataTable 빈 상태 | 등록된 도서가 0건일 때 `DataTable`의 기본 `emptyText="데이터가 없습니다."` 노출 | `DataTable` 기존 기본값. 원문 스크린샷/코드에 별도 빈 상태 문구 없음 |
| DataTable 로딩 | **미확정** — 최초 목록 조회(`GET /books/search`) 중 로딩 UI(스켈레톤/스피너) 명세 없음 | 디자인 원문에 로딩 상태 없음. 확인 필요 |
| Toast | 등록 성공 시 표시, 2.8초 후 자동 닫힘, 수동 닫기(`onClose`)도 가능, 성공 체크 아이콘 포함 | 디자인 원문 명시 |
| CountBadge | `${등록된 도서 수}건` — 정적 텍스트, 상호작용 없음 | 디자인 원문 |

## 반응형 규칙

디자인 원문(JSX)에는 브레이크포인트별 분기 코드가 없다 — **미확정, 추정치로 기술**.

- base(모바일, ~639px 추정): Grid2를 1열로 축소(`grid-cols-1`) 권장 — 기존 `AppSidebar` 레이아웃이 이미 모바일 대응을 어떻게 하는지 확인 필요. 테이블은 `DataTable`이 이미 `overflow-x-auto`로 가로 스크롤 처리(기존 컴포넌트 기능).
- md 이상(~768px+): Grid2 2열 유지(디자인 기본값).
- 액션 로우(초기화/등록 버튼): 모바일에서도 우측 정렬 유지 추정, 버튼 폭은 원문 기준 `fullWidth` 아님.
- 카드 좌우 패딩: `--spacing-page-x`(40px)가 작은 화면에서 과도할 수 있음 — **미확정**, 기존 다른 placeholder 화면들의 반응형 처리 방침을 component-architect/frontend-implementer가 통일해서 결정 필요.

## 데이터/콘텐츠 형태

**백엔드 API 계약 기준**(디자인 목업이 아님 — publisher/copies 제외).

```ts
// 등록 폼 입력값
interface BookRegisterFormValues {
  title: string;   // required, @NotBlank
  author: string;  // required, @NotBlank
  isbn: string;     // optional — 빈 문자열이면 요청 시 null 또는 미전송
}

// POST /books 요청 바디
interface CreateBookRequest {
  title: string;
  author: string;
  isbn?: string | null;
}

// POST /books 성공 응답 (201)
interface BookResponse {
  id: number;
  title: string;
  author: string;
  isbn: string | null;
  createdAt: string; // ISO-ish LocalDateTime
}

// 목록 조회 GET /books/search 응답 (하단 테이블 데이터 소스로 추정)
interface BookSearchResponse {
  books: { id: number; title: string; author: string; isbn: string | null }[];
  pagination: { page: number; pageSize: number; totalPages: number; totalElements: number };
}

// 공통 에러 응답 (RFC7807 확장)
interface ApiError {
  type: string;
  title: string;   // = code
  status: number;
  detail: string;  // 사용자 노출 메시지로 그대로 사용
  instance: string;
  code: string;     // "DUPLICATE_ISBN" | "INVALID_INPUT" | ...
  traceId: string | null;
}

// DataTable 컬럼 정의 (API 스코프로 축소됨 — 디자인 원문의 publisher/copies 컬럼 제외)
const columns = [
  { key: 'title',  label: '도서명', width: '40%' },   // width 재분배 필요 — 아래 "미확정" 참조
  { key: 'author', label: '저자',   width: '25%' },
  { key: 'isbn',   label: 'ISBN',   width: '35%', secondary: true, nowrap: true },
];
```

**하단 테이블 데이터 출처**: 디자인 원문은 정적 배열(`BOOKS`)을 참조하나, 실제 구현에서는 `GET /books/search`(기본 `pageSize=10`, 최대 100) 또는 등록 직후의 로컬 상태 반영으로 채워야 함 — **미확정, 아래 참조**.

## 미확정 항목 (사용자 확인 필요)

1. **디자인-백엔드 필드 갭 (가장 중요)** — 디자인 목업의 `출판사`(publisher) 입력 필드, 테이블의 `출판사`/`소장본 수`(copies) 컬럼은 백엔드 `POST /books` 및 `GET /books/search` 어디에도 존재하지 않는다. 이 스펙은 두 필드를 **제외**하고 시각적 레이아웃(2열 그리드, 카드 2개, 테이블, 토스트)만 유지하는 것으로 확정했다. 향후 백엔드에 필드가 추가되면 스펙 갱신 필요.
2. **하단 목록 데이터 출처** — 디자인 원문은 정적 배열(`BOOKS`)을 참조. 실제 구현에서 `GET /books/search`를 호출해 서버 페이지네이션(`pageSize` 기본 10, 최대 100)을 쓸지, 원문처럼 클라이언트 페이지네이션(`DataTable pageSize=20`)으로 전량 로드 후 자를지 결정 필요. API가 서버 페이지네이션을 제공하므로 서버 페이지네이션 권장이나, 최종 결정은 component-architect/frontend-implementer.
3. **등록 성공 후 목록 갱신 방식** — 재조회(refetch) vs 낙관적 추가(응답으로 받은 `BookResponse`를 로컬 목록 맨 위에 추가) 중 미정. 원문 코드는 정적 배열이라 이 로직 자체가 없음.
4. **테이블 컬럼 width 재분배** — 원문은 5컬럼 기준 폭(28/14/16/20/10%)이었다. 3컬럼(도서명/저자/ISBN)으로 줄어들며 폭 재분배가 필요 — 정확한 비율은 미확정, 구현 시 시각적으로 조정.
5. **Button(초기화) 정확한 동작** — "빈 값으로 리셋"인지 "최초 로드 시점 값으로 복원"인지 원문에 명시 없음. 폼에 초기값이 없으므로 실질적으로는 동일하나, 명시적 확인 필요.
6. **로딩 상태 전반** — 등록 버튼 제출 중, 목록 최초 조회 중 로딩 UI가 디자인 원문에 없음. 스켈레톤/스피너 등 구체적 형태 미확정.
7. **반응형 규칙** — 디자인 원문(JSX)에 브레이크포인트 분기 코드가 없어 전부 추정치. 모바일 그리드 1열 전환 등은 구현 시 다른 placeholder 화면들과 일관되게 통일 필요.
8. **CORS** — `api-contract.md`에 따르면 백엔드에 CORS 설정이 없어 프론트 dev 서버에서 호출 시 에러 가능성. 이 스펙 범위 밖이나 구현 단계에서 재확인 필요(보류 항목으로 이미 보고됨).
9. **Toast 컴포넌트 신규 추출 여부** — 이 화면에서는 1회 등장이라 "2회 반복이면 추출" 규약과 정확히 일치하지 않음. 다만 성공 알림은 범용 패턴이라 신규 `ui/toast.tsx` 후보로 표시했고, 최종 판단은 component-architect에게 위임.
10. **PageHeader 신규 추출 여부** — 동일하게 1회 등장. 다른 placeholder 화면(대출/반납/연체 등)에서도 쓰일 공통 패턴으로 보이나, 그 화면들의 실제 스펙은 아직 추출되지 않았음. component-architect가 향후 확장성 고려해 판단.
